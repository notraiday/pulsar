# Live-диалоги

Live — это разговор с колонкой в обе стороны сразу: микрофон остаётся открытым, пока колонка
отвечает, и ответ можно перебить голосом. Колонка в нём — тонкий клиент: гонит звук микрофона на
«мост» (небольшой сервис в `live/bridge/`), играет то, что пришло, и показывает состояние. Всё
остальное — какая модель отвечает, когда реплика закончилась, ходить ли к домашнему агенту,
отдать ли диалог Home Assistant — решает мост. Выбора режима на колонке нет: мост не задан — отвечает
Home Assistant, как раньше.

Код колонки: крейт `satellite/crates/pulsar-live/` и `controller/live.rs`. Код моста: `live/bridge/`.

## Как это сосуществует с обычным сценарием (Home Assistant)

| Ситуация | Что происходит |
|---|---|
| Мост не задан (по умолчанию) | Ничего не меняется: Assist-конвейер Home Assistant, как до Live. Код Live не запускается. |
| Мост задан, диалог по активационной фразе или кнопке | Живой диалог через мост. |
| Мост недоступен (нет сети, порт закрыт, 3 с) | Колонка запускает конвейер HA и скармливает ему уже сказанное (до 3 с звука): первые слова не теряются. |
| Не открылся вывод звука для ответов | То же самое: конвейер HA. |
| Мост отвечает кадром `R` («не беру») | То же самое: конвейер HA, ему повторяются последние ~1,5 с микрофона. Так мост по имени колонки или по состоянию бэкенда отдаёт диалог HA. |
| Бэкенд моста не смог стартовать (нет ключа, облако отказало) | Мост сам отвечает `R`, колонка отвечает через HA. |
| Связь оборвалась посреди диалога | Диалог кончается; доигрывается то, что уже пришло. Продолжения через HA нет. |
| Таймеры, объявления, музыка | Работают как раньше. Во время Live-диалога музыка приглушается. |
| `assist_satellite.start_conversation` (напоминание), мост задан | Live-диалог, который начинает дом: без звука-подтверждения колонка открывает диалог с текстом сообщения в приветствии (`reminder`), мост говорит его и слушает ответ (см. «Напоминания»). HA получает AnnounceFinished, как только мост взял диалог (его первое состояние). Мост не взял (недоступен, `R`, сбой до первого состояния) — объявление как раньше, затем конвейер HA. Во время другого диалога или объявления, при выключенном микрофоне — тоже как раньше. |

Звук Live идёт мимо Home Assistant: Assist-конвейер HA пошаговый (распознавание → агент → озвучка),
слушать во время ответа и перебивать голосом в нём нельзя, поэтому дуплекс держит мост. Запросы к
домашнему агенту (всё, что касается дома и личных данных) мост по умолчанию шлёт агенту напрямую
(в дом агент ходит сам, например через MCP-сервер HA); по выбору — **через Home Assistant**, тому
же агенту диалога, что стоит в голосовом конвейере, от имени колонки (см. «Домашний агент» ниже). Если перед агентом стоит роутер моделей, мост помечает такие
запросы префиксом `@@LIVE@@` (см. `HERMES_MARK`), по которому роутер отправляет их в облачную
модель без локального быстрого пути и снимает метку перед моделью. Обычные запросы HA метки не
несут и роутером не меняются.

## Настройка колонки

Адрес моста — `host:port`. Задаётся одним из двух способов; файл имеет приоритет и читается при
каждом диалоге, перезапуск не нужен:

```sh
/data/pulsar/ctl.sh live-bridge 192.168.1.50:10700   # файл /data/pulsar/live_bridge
/data/pulsar/ctl.sh live-bridge                      # показать
/data/pulsar/ctl.sh live-bridge off                  # выключить: отвечает HA, что бы ни стояло в state.conf
/data/pulsar/ctl.sh live-bridge clear                # убрать файл
```

Второй способ — ключ `live_bridge=host:port` в `state.conf`. Его пишет демон (вместе с
`voice_mode=Live`, который читает C++-сборка Live, поэтому откат на неё работает), и только когда
ключ не пуст.

## Что делает колонка

- Активационная фраза или кнопка начинают диалог: звук-подтверждение, микрофон идёт на мост (с
  предзвуком — тем, что сказано после фразы), музыка приглушается, кольцо и часы показывают
  состояние от моста (`listening` / `thinking` / `speaking`).
- Ответ играет собственный ALSA-поток (`Model::playback_pcm`, 24 кГц, моно, период 20 мс, буфер
  125 мс), в обход плеера на GStreamer; он смешивается с музыкой и звуками через dmix. Громкость —
  общая колонкина; «громче» / «тише» работают в диалоге.
- Активационная фраза во время диалога только обрывает воспроизведение. Заканчивают диалог:
  кнопка, «стоп», выключатель микрофона, мост (кадр `X`: ушёл в тишину, попрощались, закончился
  лимит) и лимит 15 минут. После `X` досказывается то, что уже в очереди воспроизведения (до 20 с).
- Эхо собственного голоса вычитает VQE ещё в колонке, так что мост получает чистый микрофон, а
  перебивание решает его детектор речи.

## Протокол

Кадры в обе стороны: `[u8 тип][u32 LE длина][нагрузка]`, нагрузка не больше 8 МиБ. Одно
TCP-соединение — один диалог.

| Направление | Тип | Нагрузка |
|---|---|---|
| колонка → мост | `H` | JSON-приветствие: `{"wake_word":…,"station":"<имя устройства>","protocol":1}`, у диалога, который начал дом, ещё `"reminder":"<текст>"`; всегда первый кадр |
| колонка → мост | `A` | микрофон, s16le, 16 кГц, моно, уже очищенный VQE |
| колонка → мост | `D` | воспроизведение доиграло всё полученное |
| колонка → мост | `E` | колонка заканчивает диалог (причина) |
| мост → колонка | `A` | ответ, s16le, 24 кГц, моно |
| мост → колонка | `F` | сбросить очередь воспроизведения (перебили) |
| мост → колонка | `S` | состояние кольца: `listening`, `thinking`, `speaking` |
| мост → колонка | `X` | диалог закончен (причина) |
| мост → колонка | `R` | мост диалог не берёт: колонка запускает конвейер HA |

Неизвестные типы колонка пропускает. C++-сборка Live на Миди (прежняя) тоже пропускает неизвестные
кадры, то есть `R` для неё ничего не значит: бэкенд `handoff` и отступление на HA работают только
для колонок с этой (Rust) сборкой.

## Мост (`live/bridge/`)

Python 3.12, `aiohttp`, `pysilero-vad`. Запуск (ключи только из окружения, в репозиторий они не
попадают):

```sh
docker build -t pulsar-live-bridge live/bridge
docker run -d --restart unless-stopped --name live-bridge -p 10700:10700 \
  --env-file bridge.env -v "$PWD/conf:/conf" \
  -e LIVE_ROUTES=/conf/routes.json -e LIVE_INSTRUCTIONS=/conf/instructions.txt pulsar-live-bridge
```

`conf/` — каталог (не одиночные файлы: правка с заменой файла рвёт bind-mount одного файла) с
`routes.json` и `instructions.txt`; образцы лежат рядом с мостом (`*.example.*`). Оба файла
перечитываются на каждый диалог.

### Маршруты и «горячая» замена бэкенда

Бэкенд диалога выбирается по имени, которое колонка шлёт в приветствии (`routes.json`, см.
`livebridge/routes.py`): шаблоны `fnmatch`, первое совпадение выигрывает, иначе `default`;
`fallback` (по умолчанию `handoff`) берёт диалог, если выбранный бэкенд не стартовал. Файл
перечитывается при изменении, так что переключить колонку с одной модели на другую — правка одной
строки, без перезапуска моста и колонки; битый файл не применяется (остаётся прежний).

Бэкенд — модуль в `livebridge/backends/` с `async def run(station, http, options)`; имя
бэкенда — имя файла (`-` читается как `_`). Новый файл подхватывается без перезапуска; правка уже
загруженного модуля — только с перезапуском. До первого слова колонке бэкенд может бросить
`BackendUnavailable` (или любое исключение) — мост ответит `R`.

| Бэкенд | Что это |
|---|---|
| `pipeline` | Основной. Silero VAD ищет конец реплики, модель чата (OpenRouter, по умолчанию `deepseek/deepseek-v4.1-flash`) получает её расшифровку (или звук, см. ниже), ответ режется на предложения и озвучивается TTS по мере написания; инструмент `ask_hermes` (домашний агент, см. ниже) и `end_dialog` (на «ок, спасибо», «пока», «хватит»: диалог закрывается сразу, без ещё одного раунда модели и без прощания); результаты, пришедшие после перебивания, озвучиваются потом. Первый ход диалога, который начал хозяин, сразу уходит агенту расшифровкой, параллельно с раундом модели (см. «Скорость»). Опции: `llm`, `tts_voice`, `instructions` и опции агента. |
| `gpt-live` | **Экспериментальный.** OpenAI `gpt-live-1` (полнодуплексная модель, `wss://api.openai.com/v1/live/sessions`): модель сама слушает и говорит, мост шлёт ей звук, отдаёт колонке её голос, режет очередь колонки по перебиванию (тот же Silero) и отвечает на делегирование («client delegation») запросом к домашнему агенту. Написан по документации и проверен только на поддельном сервере: на настоящем сервисе не запускался, имена событий, заголовки и эвристику перебивания, возможно, придётся поправить. Нужен `OPENAI_API_KEY`; при `LIVE_ZDR` (по умолчанию) ещё `LIVE_GPT_ZDR=1` — подтверждение, что у организации OpenAI есть нулевое хранение, иначе диалог уходит колонке (`R`). Опции: `voice`, `model`, `instructions` и опции агента. |
| `handoff` | Всегда `R`: колонка отвечает через HA. |
| `test` | Без модели: тон 440 Гц и замер, как громко его слышит микрофон (проверка эхоподавления). |

### Локальное распознавание (GigaAM)

С `LIVE_STT_URL` (OpenAI-совместимый `/audio/transcriptions`, например GigaAM; `LIVE_STT_KEY`,
`LIVE_STT_MODEL` = `v3_e2e_rnnt`, `LIVE_STT_LANGUAGE` = `ru`, `LIVE_STT_TIMEOUT` = 3 с) реплики
распознаёт локальный распознаватель (`livebridge/stt.py`), а `LIVE_INPUT` решает, что получает модель:

| `LIVE_INPUT` | Модель получает | |
|---|---|---|
| `text` (по умолчанию со STT) | только расшифровку | быстрее всего: на живых репликах первое действие Gemini — медиана 1,09 с против 1,79 с со звуком, и подходит любая текстовая модель; персона знает, что слышит расшифровку (`[SILENT]` — только на явную бессмыслицу или чужой разговор) |
| `both` | расшифровку рядом со звуком | |
| `audio` (по умолчанию без STT) | только звук | как без распознавателя |

Расшифровка запускается заранее, на первых `LIVE_STT_SPEC_MS` (250 мс) тишины, пока детектор ещё
ждёт конца реплики, поэтому к концу хода она готова; если хозяин продолжил — её отбрасывают. Не
распознал (ошибка, таймаут) — ход идёт звуком; в расшифровке нет слов — ход не отвечается.
Реплику короче порога детектора (меньше `LIVE_MIN_SPEECH_MS` голоса, быстрое «удали их») мост не
выбрасывает как шум, если в её расшифровке есть слова (от `LIVE_STT_RESCUE_MIN_MS`, 96 мс). Каждая
расшифровка — в логе. Ответ, который перебили, не теряется: в следующем раунде модели прямо сказано,
что хозяин его ещё не слышал. `LIVE_LOG_FILE` — лог ещё и в файл (4 × 5 МиБ), переживает
пересоздание контейнера.

### Очерёдность реплик: как с живым человеком

- **Не обрывать на полуслове.** Если расшифровка, сделанная на паузе, кончается словом, за которым
  мысль явно продолжается («включи свет в…», «купи хлеб и…», «что», «потому», «ну», запятая), пауза
  до конца реплики — `LIVE_END_SILENCE_LONG_MS` (1400 мс) вместо `LIVE_END_SILENCE_MS` (600 мс).
  Распознаватель ставит точку или «?» в конце любой расшифровки (недоговорённое часто звучит как
  вопрос: «Сколько будет два +?»), поэтому смотрится последнее слово: предлоги, союзы и знаки («+»,
  «=», запятая) продолжают мысль всегда, а слова, которыми кончаются вопросы («как?», «что?»), — только
  без «?». В режимах `text` / `both` ход и так ждёт эту расшифровку, так что ожидание её на паузе
  ничего не стоит.
- **Не говорить поверх хозяина.** Пока ответ только готовится (ничего не играет, эха нет), речь
  хозяина слышна сразу, с `LIVE_START_MS`, а не с `LIVE_BARGE_MS`: ответ ждёт и не начинает звучать,
  пока хозяин говорит. Сказал короткое «три» — это продолжение его хода (ниже); шум без слов — ответ
  звучит дальше как был. Набралось `LIVE_BARGE_MS` речи — начатый ответ обрывается сразу.
- **Продолжение — тот же ход.** Хозяин договорил («Включи свет»), пауза кончилась, модель начала
  думать, — и он продолжил («…в спальне») в пределах `LIVE_MERGE_S` (2,5 с) от конца хода и до того,
  как услышал хоть слово ответа: начатый ответ выбрасывается целиком (его просьбы агенту
  останавливаются, новые дела забываются), а новая реплика дописывается к его ходу — модель получает
  один ход «Включи свет. В спальне». Если какая-то просьба агенту уже успела выполниться, ход не
  склеивается (она что-то сделала, модель должна это видеть). Если «продолжение» оказалось шумом или
  в его расшифровке нет слов, прерванный ход отвечается заново, а не пропадает. Ход, на который
  модель промолчала (решила, что хозяин не договорил), тоже принимает следующую реплику, если она
  пришла в пределах `2 × LIVE_MERGE_S`.
- **История помнит, что хозяин услышал.** Когда хозяин перебивает ответ, мост по отправленному звуку
  (24 кГц, колонка играет его подряд) оценивает, сколько успело прозвучать (с поправкой
  `LIVE_HEARD_LAG_S`, 0,3 с: задержка колонки и первые слова хозяина поверх ответа), и в истории
  остаётся только это: целые сыгранные предложения и начало прерванного («Раз два…») с пометкой
  `[тут хозяин тебя перебил]` (сама пометка никогда не произносится). Не прозвучавшее модель
  считает несказанным.
- **Свои короткие фразы — разные.** То немногое, что мост говорит сам, без модели (подтверждение кода
  или «да», «не расслышала», начало чужого вопроса посреди другого разговора), берётся из нескольких
  вариантов и не повторяется дважды подряд (`livebridge/phrases.py`). «Это надолго, займусь»
  говорит модель своими словами.

### Нулевое хранение данных (ZDR) и скорость

`LIVE_ZDR` (по умолчанию включено, `0` — выключить): всё, что мост шлёт в облако, уходит только на
конечные точки с нулевым хранением. Каждый запрос к OpenRouter (модель и TTS) несёт
`provider: {zdr: true, data_collection: deny}` — и при подстраховочном втором запросе, и при повторе
после ошибки. У Gemini такие точки только на Vertex (AI Studio данные хранит), у ElevenLabs — все.
`gpt-live` идёт в OpenAI напрямую и без `LIVE_GPT_ZDR=1` не стартует. Распознавание (GigaAM) локальное;
агент Hermes ходит в облако через свой роутер, там тоже `zdr: true`.

Модель чата и её маршрут (`pipeline.py`: `provider_for`, `reasoning_for`; `LIVE_LLM`,
`LIVE_LLM_PROVIDER` — JSON вместо маршрута по умолчанию, `zdr` добавляется всегда; `LIVE_REASONING`).
Замер 2026-10-27 на 42 живых ходах (одна реплика и куски настоящих диалогов, точки ZDR), медиана / p90
до решения (вызов инструмента целиком или первое предложение):

| Модель (точки) | Решение | Верных действий |
|---|---|---|
| `deepseek/deepseek-v4.1-flash` (Together, Baseten, InferenceNet; без рассуждений) — **по умолчанию** | 0,53 / 0,76 с | 42 из 42 |
| `google/gemini-3.5-flash-lite` (Vertex) | 0,71 / 1,01 с | 42 из 42 |
| `google/gemini-3.6-flash` (Vertex, `effort: minimal`) | 0,93 / 1,50 с | 39 из 42 |

Что ещё сокращает ожидание:
- **Агент на первом ходе — сразу.** У первого хода диалога, который начал хозяин (не напоминание),
  нет контекста: его расшифровка уже самодостаточная просьба. Мост сразу отправляет её агенту и
  параллельно спрашивает модель; если модель тоже зовёт `ask_hermes` (почти всегда: первый ход — это
  команда), она получает ответ уже идущего запроса, на время её раунда (~0,5 с) раньше; если отвечает
  сама, завершает диалог или молчит, ранний запрос отбрасывается. `LIVE_AGENT_RACE=0` — выключить.
- **Два соединения заранее.** Новое соединение через прокси стоит ~0,34 с против 0,07 с у живого;
  на открытии диалога мост открывает два (поток модели и TTS первого предложения идут одновременно).
- **Подстраховка.** Модель молчит `LIVE_LLM_HEDGE_S` (1,5 с) — второй такой же запрос (точки в
  обратном порядке), выигрывает первый ответивший. TTS без звука `LIVE_TTS_HEDGE_S` (0,8 с) — так же:
  OpenRouter отдаёт звук ElevenLabs целиком (0,27 с на пару слов, ~0,45 с на 130 знаков), но
  изредка — через 1–1,5 с.

Поддельная колонка (`tools/e2e.py`) от конца вопроса до первого звука ответа: погода и температура
через агента 2,0–2,4 с (было 3,5–3,9 с), шутка без агента 1,3 с, календарь — вступление 1,4 с. Теперь
путь держит агент: два раунда его модели по 0,4–0,6 с плюс инструмент. `eleven-flash-v2.5` через
OpenRouter не быстрее `eleven-turbo-v2.5`.

### Напоминания: диалог начинает дом

Колонка, получив от HA `start_conversation`, открывает диалог с `reminder` в приветствии. Бэкенд
`pipeline` (`livebridge/reminders.py`) собирает в группу диалоги с одинаковым текстом, открытые в
пределах `LIVE_REMINDER_JOIN_S` (3 с), один раз синтезирует весь текст (теги вроде `[emo:good]`
снимаются; остальные колонки тем временем подключаются, не меньше `LIVE_REMINDER_GATHER_S`, 0,35 с)
и шлёт всем колонкам группы один и тот же звук: колокольчик и сразу за ним слова, без паузы на
синтез (`LIVE_REMINDER_SOUND` — свой wav, `off` — без колокольчика; по умолчанию встроенный); опоздавшая получает его с того места, где остальные. Пока говорят несколько колонок, никто
не слушает: каждая слышит голос соседки, а его эхоподавление не вычитает. Когда все доиграли
(+0,3 с), слушают все; первая реплика открывает окно `LIVE_REMINDER_DECIDE_S` (0,35 с), отвечает
колонка, которая слышит хозяина громче (средний уровень его голосовых кадров), остальные
заканчивают диалог (`X`, «another station answers»). Одна колонка — то же самое, и напоминание
можно перебить голосом. Модель знает, что сказала (дописка к персоне): «ок», «спасибо» — сразу
`end_dialog`, «напомни через час» — новое напоминание через агента. `gpt-live` диалоги с
`reminder` не берёт (`R`: колонка объявит как раньше).

Чтобы агент начинал такие диалоги, в HA нужен способ вызвать `start_conversation` на всех колонках,
например скрипт, открытый для Assist (он становится инструментом MCP-сервера HA):

```yaml
live_reminder:
  alias: Напоминание голосом
  description: Колонки говорят текст и ждут ответа хозяина.
  fields:
    message: {description: Что сказать, required: true, selector: {text: {}}}
  sequence:
    - action: assist_satellite.start_conversation
      target: {entity_id: [assist_satellite.kitchen, assist_satellite.bedroom]}
      data: {start_message: "{{ message }}", preannounce: false}
```

### Домашний агент

Модель диалога сама в дом не ходит: для всего, что касается устройств, таймеров, календаря, денег,
почты, погоды и памяти, она зовёт домашнего агента (в `pipeline` — инструмент `ask_hermes`, в
`gpt-live` — делегирование). Как мост до него добирается (`livebridge/agent.py`), задаёт
`LIVE_AGENT` или опция маршрута `agent`:

| `agent` | Куда идёт запрос |
|---|---|
| `ha` | `POST /api/conversation/process` Home Assistant (`HA_URL`, токен `HA_TOKEN`) агенту `HA_AGENT_ID` — тому же, что в голосовом конвейере колонки (*Настройки → Голосовые ассистенты → конвейер → Агент диалога*, например `conversation.extended_openai_conversation`, за которым стоит Hermes). Запрос попадает в журнал диалогов HA, агент знает, какая колонка спрашивает (опции маршрута `ha_satellite_id` — сущность `assist_satellite.…` колонки — или `ha_device_id`: контекст комнаты), а смена агента в HA меняет его и для Live. Один Live-диалог — один разговор HA (`conversation_id` переносится между запросами; одновременные запросы получают каждый свой). |
| `hermes` (по умолчанию) | Прямо в OpenAI-совместимый адрес агента (`HERMES_URL`, `HERMES_KEY`) мимо HA; в дом агент ходит сам (например, через MCP-сервер HA). |

Отступления с одного пути на другой нет: если HA не ответил, модель узнаёт, что запрос не
выполнен, и говорит об этом. Без `HA_URL` / `HA_TOKEN` при `agent=ha` бэкенд не стартует, и
диалог уходит колонке (`R`): она отвечает через конвейер HA, как без моста.

`HA_TOKEN` — долгоживущий токен пользователя HA (*Профиль → Безопасность → Долгоживущие токены
доступа*); кладётся только в окружение моста (`bridge.env`). Без `HA_AGENT_ID` отвечает агент HA по
умолчанию (встроенные интенты), а не Hermes. Метка `@@LIVE@@` видна в журнале диалогов HA: её
снимает роутер, а не HA.

Задержку пути можно проверить из окружения моста (агент выполняет запрос по-настоящему, поэтому
только вопросы, которые ничего не меняют):

```sh
docker exec live-bridge python -m livebridge.probe --agent both -n 3 "Который час?"
```

Переменные окружения моста: `LIVE_LISTEN`, `LIVE_ROUTES`, `LIVE_DEFAULT_BACKEND`, `LIVE_INSTRUCTIONS`;
агент: `LIVE_AGENT` (`hermes` | `ha`), `HA_URL`, `HA_TOKEN`, `HA_AGENT_ID`, `HA_LANGUAGE` (`ru`),
`LIVE_HA_KEEP_CONVERSATION` (`1`; `0` — каждый запрос отдельным разговором), `LIVE_AGENT_TIMEOUT`
(иначе `HERMES_TIMEOUT`, 1800 с: фоновые просьбы тоже), `LIVE_AGENT_SILENT_S` (900), `HERMES_URL` / `HERMES_KEY`, `HERMES_MARK`; вопросы агента: `LIVE_SURFACE_LISTEN`, `LIVE_SURFACE_TOKEN`, `LIVE_ASK_TIMEOUT_S` (120), `LIVE_AGENT_DETACH_S` (20); `pipeline`: `OPENROUTER_API_KEY`,
`LIVE_ZDR`, `LIVE_OR_PROXY`, `LIVE_LLM`, `LIVE_LLM_PROVIDER`, `LIVE_REASONING`, `LIVE_LLM_HEDGE_S`,
`LIVE_TTS`, `LIVE_TTS_VOICE`, `LIVE_TTS_HEDGE_S`, `LIVE_AGENT_RACE` и остальные `LIVE_*` (заголовок
`pipeline.py` и `session.py`); `gpt-live`: `OPENAI_API_KEY`, `LIVE_GPT_URL`, `LIVE_GPT_MODEL`,
`LIVE_GPT_VOICE`, `LIVE_GPT_PROXY`, `LIVE_GPT_HEADERS`, `LIVE_GPT_DROP_GAP_S`, `LIVE_GPT_ZDR`.

### Агент спрашивает хозяина, долгие просьбы

Голосовой агент работает и с сайтами (браузер в песочнице, `handoff/browser-sandbox/`): заказать,
забронировать, войти. Посреди дела ему бывает нужен хозяин: код из SMS, «да» перед оплатой, выбор.
Для этого у моста есть вход для агента (`livebridge/surface.py`, `LIVE_SURFACE_LISTEN`, например
`0.0.0.0:10702`, с токеном `LIVE_SURFACE_TOKEN`), а у Hermes — плагин `live/hermes-plugin/voice-surface`:

- **Вопрос** (`POST /ask`, виды `code` / `confirm` / `text`) звучит в том Live-диалоге, который начал
  эту сессию агента: каждую просьбу мост отправляет в сессии со своим именем (`X-Hermes-Session-Id:
  live-…`, нужен `HERMES_KEY`). Ответ хозяина уходит только агенту: модель диалога его не видит, в
  историю он не попадает. Код не пишется ни в лог, ни в дамп; агент тоже его не видит: Hermes вводит
  цифры в страницу сам (`browser_vault_enter_code`). Число словами читается так, как диктуют коды
  («сорок пять двенадцать» = 4512, `spoken.py`). «Да/нет» решается в пользу «нет»: любое «не»,
  «стоп», «отмена» — отказ.
- **Того диалога уже нет** (просьба ушла в фон), но хозяин в другом Live-диалоге — вопрос звучит в
  нём, с коротким началом вроде «Слушай, …» (колонка в Live-диалоге отказывает HA в `start_conversation`,
  поэтому будить её нельзя). **Диалогов нет совсем** — мост отвечает `wake`: плагин будит колонки
  скриптом HA `script.live_reminder` с текстом вопроса, и диалог, который откроется, примет ответ (как
  ответ на напоминание).
- **Просьба, которую диалог бросил** (модель ответила сама, разговор оборвали) — её сессия «брошена»:
  вопросы из неё получают `no_answer` сразу, никого не будят, итог не объявляется.
- **Долгая просьба**: если агент не ответил за `LIVE_AGENT_DETACH_S` (20 с), модель диалога своими
  словами говорит, что это надолго и что она позовёт, если понадобится, и просьба идёт в фоне. Пока диалог жив,
  итог звучит в нём; когда диалог закончился, плагин после хода агента спрашивает мост (`POST
  /result`): итог говорит Live-диалог, который сейчас идёт, а если его нет — плагин объявляет через
  колонки короткую выжимку, которую пишет модель диалога голосом персоны (две фразы, без зачитывания
  списков: «Все десять городов собрала… Рассказать подробно?»). Диалог, который открывает это
  объявление, привязан к делу: подробности модель берёт из полного итога, а «добавь ещё
  Владивосток» продолжает то же дело в его сессии. Объявляются только сессии, начатые Live-диалогом (обычный конвейер HA свои ответы
  говорит сам).
- **Журнал голосовых дел.** После каждого хода голосового агента плагин пишет строку в хранилище
  Obsidian (`log_dir`, по умолчанию `/srv/vault/Агент/Голос/ГГГГ-ММ-ДД.md`): «17:05 — Нашла билеты в
  Казань на пятницу, от 4 500 ₽.» Мелочи (приветствие, время, погода, арифметика) не пишутся. Личного
  в журнале нет: строку пишет вспомогательная модель с правилом «без имён, контактов, адресов, сумм,
  переписки, кодов, здоровья», а для хода, где понадобились личные данные (любой инструмент вне
  безопасного списка: почта, деньги, браузер, заметки, память, ответы хозяина), она получает только
  слова хозяина, без ответа и результатов, причём как результат небезопасного инструмента
  (`voice_private_turn`), поэтому роутер держит этот запрос на локальной модели. Инструмент
  `voice_log` (дни, слова) читает журнал, когда хозяин спрашивает о прошлом («что я просил вчера?»);
  роутер считает его безопасным (`EXTRA_SAFE_TOOLS`), сессию он не «заражает».
- **Дела.** Для хозяина агент и модель диалога — одна Алёна: о работе агента она говорит от себя
  («Добавлю», «Заказала»), без «передала» и «агент» (правило в персоне, описание `ask_hermes`,
  заметки от первого лица). С `HERMES_KEY` каждая просьба — запуск (run) Runs API Hermes в сессии,
  которую называет мост: его можно направить на ходу (`/steer`: агент получит слова после текущего
  шага), остановить (`/stop`) и потом продолжить в той же сессии со всей историей. Задачи для сайтов
  и ушедшие в фон просьбы модель каждого диалога видит как свои дела с номерами: что просили, сколько
  идёт, текущий шаг и последняя заметка агента по ходу, или полный итог (законченные — ещё 30 минут).
  Реплику хозяина модель сама относит к делу или к новой просьбе: `ask_hermes(task=N)` с его словами
  как есть идущее дело направляет («лучше пепперони» доходит до агента посреди заказа, в ответ —
  «Хорошо, возьму пепперони» от себя), законченное продолжает в его сессии («а когда привезут?» —
  агент помнит заказ); без `task` — новая сессия. «Как там пицца?» модель
  отвечает по списку, «отмени» — `stop_background`. Пока в списке есть задачи, первый запрос агенту
  не стартует до решения модели (иначе слова про задачу ушли бы новой просьбой). Итог задачи
  говорится один раз: кто первым сообщил — плагин (`/result`) или вернувшийся запрос.
- **Задачи для сайтов думают с самого начала**: модель диалога помечает их (`ask_hermes(browser=true)`),
  плагин узнаёт это у моста (`GET /session/ID`) или видит, что агент уже взялся за браузер, и
  помечает вызовы модели полем `hermes_live_think`; роутер перед агентом (litellm-taint)
  отправляет их в модель `cloud-think` — та же модель с рассуждением. Так же думает любая просьба,
  ушедшая в фон. Исключение — «система 1»: шаг сразу после удачного действия в браузере (нажать,
  ввести текст, прокрутить, заполнить из хранилища) механический (обычно — посмотреть страницу) и
  идёт быстрой моделью, не больше трёх раз подряд; страницу читает и решает, что делать, думающая.
- Мост озвучивает только последнее сообщение агента (после последнего инструмента), без его
  реплик между шагами.

Плагин (кладётся в `~/.hermes/profiles/voice/plugins/voice-surface`, включается в
`plugins.enabled` профиля, инструменты — набор `voice_surface` в `platform_toolsets.api_server`)
делает это только в api_server-сессиях профиля `voice`: включает Hermes-у подсказки, которые в
api_server выключены (код, подтверждение карты голосом: «Ввести карту … на сайте …? Да или нет?»),
добавляет агенту инструмент `ask_owner` и объявление итогов. Токен моста — в
`<профиль>/voice_surface.token`. Файл `<профиль>/voice_surface.nowake` выключает побудку колонок
(вопросы без диалога тогда не задаются, итоги не объявляются) — для тестов и тихих часов.

Пароли, карты и адреса — только из хранилища Hermes; плагин подключает весь Vaultwarden (CLI `bw`):
`sudo hermes-bw-unlock` на сервере Hermes (`--login` — первый вход) спрашивает мастер-пароль и
оставляет только ключ сессии в RAM (`/run/user/<uid>/hermes-bw/session`) до перезагрузки или
`hermes-bw-lock`. Логины, карты (оплата) и личности с адресом видны агенту только по названию;
вводятся в страницу без него. Карта и адрес вводятся только на сайтах из поля `hermes_sites` записи
(origin через запятую, только https), карта — после «да» голосом.

### Тесты

```sh
cd live/bridge && python -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q tests
```

Ключи и сеть не нужны: OpenRouter, Home Assistant, домашний агент и OpenAI заменены локальными
поддельными серверами; тесты ничего не включают и не говорят. Ручные проверки на настоящем сервисе —
`tools/e2e.py` и `tools/two_utt.py` (поддельная колонка синтезирует вопрос через TTS и меряет
задержки; нужен `OPENROUTER_API_KEY` в окружении) и `tools/stub_hermes.py` (агент-заглушка с
готовыми ответами, без побочных действий).

## Ограничения

- Одна колонка — один диалог; несколько колонок мост обслуживает параллельно.
- Нет выбора режима на самой колонке и сущности в HA для него: адрес моста — настройка
  устройства, а решение принимает мост.
- Когда мост недоступен, фраза на самой колонке начинает конвейер HA с задержкой до 3 с
  (таймаут соединения).
- Диалог живёт не дольше 15 минут и не переживает обрыва связи.
- Звук, сказанный сразу после активационной фразы, до открытия соединения не теряется (уходит
  первым), а вот звука *до* фразы колонка не хранит. Заготовленная фраза-заглушка («секунду») из
  прежнего моста не переносилась: модель сама говорит вступление перед долгой просьбой.
